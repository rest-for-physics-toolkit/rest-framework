Detailed Description

Orders the hits (nodes) of each track along the shortest path through all of them, e.g. after TRestTrackReductionProcess. The output event holds one track per input track.

Author
Javier Galán javie.nosp@m.r.ga.nosp@m.lan@u.nosp@m.niza.nosp@m.r.es
JuanAn García juana.nosp@m.ngp@.nosp@m.uniza.nosp@m.r.es

Orders the hits of each track of a TRestTrackEvent, of any type (XZ, YZ, XYZ, ...), along the shortest path through all of them (travelling salesman, TRestHitsAnalysis::GetShortestPath), so that the hit order follows the track, e.g. for the length and twist observables of TRestTrackAnalysisProcess. Meant for reduced tracks (TRestTrackReductionProcess), with a few tens of nodes:

  • Up to maxExactNodes hits (at most 16): the shortest path (Held-Karp dynamic programming, time and memory growing as 2^n).
  • More hits: the shortest of the nearest neighbour paths starting at every hit (at the farthest hit from the centroid above 200 hits), improved with 2-opt (reversing segments of the path while it gets shorter). Usually the shortest path or close to it, but not always.

The path is open (from any hit to any other) or, with cyclic, closed (it comes back to the first hit). The distances use the coordinates the track defines. The direction of the path is arbitrary (see TRestTrackLineAnalysisProcess for the origin and end of a track).

Observable Branches: the largest number of jumps of a track of the event, a jump being a step between consecutive hits of the ordered track longer than branchFactor times the median step of the track (0 for tracks with less than 2 steps or not ordered). 0 for a continuous track; more than 0 for gaps or branches, e.g. two particles or a fluorescence photon joined to the track.

The output event holds one track per input track (parent ID = ID of the input track) with the same hits (position, energy, time, type and sigma) in the new order, or as they are if the track has hits of different types (the undefined coordinates would mix with the defined ones). The number of tracks not ordered is reported at the end of the processing (and each one in debug).

Parameters

  • cyclic: closed path (default false).
  • maxExactNodes: maximum number of hits for the exact shortest path (default 12, at most 16).
  • branchFactor: a step longer than branchFactor times the median step is a jump (default 3).

Example:

trackPathMinimization: class: "TRestTrackPathMinimizationProcess" cyclic: false maxExactNodes: 12 branchFactor: 3 observables:

  • "Branches"

Migrated from the legacy track library (Javier Galan, JuanAn Garcia). Differences: the legacy methods (minMethod: default, bruteforce, closestN) are replaced by maxExactNodes; the default method used the Held-Karp solver of Concorde (academic licence, not included), which solves a closed path and then rotated it, now the exact path is open unless cyclic; nearest neighbour is improved with 2-opt; weightHits (unused) removed; the output event holds only the tracks of this stage (no levels). The Branches observable comes from the legacy TRestTrackReconnectionProcess (branches, not migrated: the path is already the shortest one), which counted the steps longer than mean + nSigmas * sqrt(mean) after breaking and reconnecting the track; the median keeps the jumps themselves from raising the threshold.
